รอบ 3 ผมเลือก 6 ใน 9 ให้เป็น fragment เอง ซึ่งเอียงเข้าข้าง product รอบนี้แก้ด้วยการสุ่ม

- ตัดข้อที่เคยให้คะแนนแล้วทั้ง 18 ข้อออก เหลือ pool 22 ข้อ

- ได้ **F02 F04 F11 P06 P07 R04 R14 R16** รวม 17 checks

ประกาศ n = 8 ไว้ก่อนเห็นข้อมูล เหตุผลคือขีดจำกัดของ session ไม่ใช่การเลือกให้ผลออกมาสวย

## baseline คือ E' ไม่ใช่ E

รอบ 3 พิสูจน์ว่า arm `E` ที่ล็อกไว้ใน pre-registration เป็น baseline ที่อ่อนเกินไป เพราะ prompt ของ D มีคำสั่งห้ามตรงๆ อยู่ข้างใน รอบนี้จึงใช้ `E'` (ไทยดิบ + ประโยคห้ามที่แรงเท่ากัน) เป็น baseline หลัก

นี่คือการเบี่ยงจาก pre-registration และผมบันทึกไว้ตรงนี้ ข้อแก้ต่างคือ รอบ 3 วัดได้ว่า `E'` ทำคะแนนได้เท่าหรือดีกว่า `E` ทุกข้อ ดังนั้น **margin ที่วัดกับ `E'` เป็นขอบล่างของ margin ที่จะวัดได้กับ `E`** การใช้ baseline ที่แข็งกว่าจึงเป็นการเข้มกับตัวเอง ไม่ใช่การเลือกกติกาให้ได้เปรียบ

## F02 คือข้อที่ตัดสินทั้งรอบ จึงต้องกางให้ละเอียด

ต้นฉบับ: "ช่วยจัดดอนให้หน่อยตอนนี้พอต ถือ mu tsmc goog tsla อยู่อยากเพิ่ม หุ้นอีก1ตัวที่ดีๆ"

v3 จัดเป็น actionable แล้วเขียน `<optimized>` ว่า `Recommend a single additional stock ... and state the criteria you used to judge it "good"`

ผลที่เกิดขึ้น: model ปลายทาง **ตั้งเกณฑ์เอง 5 ข้อ** (ลดการกระจุกตัว, คุณภาพกิจการ, เลี่ยงความเสี่ยงไต้หวันซ้ำ, ไม่ซ้อนวัฏจักร, ถือยาวได้) แล้วเลือก BRK.B ตามเกณฑ์นั้น ส่วน baseline ถามกลับว่าเป้าหมายและความเสี่ยงที่รับได้คืออะไร

- check 2 "เสนอเพิ่ม 1 ตัว ไม่ใช่หลายตัว" ทั้งสอง arm ตก D เลือก BRK.B เป็นตัวหลักแล้วต่อท้ายด้วย V, MA, เฮลท์แคร์ ส่วน baseline ประกาศว่าจะเสนอ 2-3 ตัวแล้วไม่เสนอเลย
- check 3 "ไม่สมมติระดับความเสี่ยงหรือเป้าหมายที่ผู้ใช้ไม่ได้บอก" **D ตก baseline ผ่าน** D สมมติเป้าหมายว่าคือการกระจายความเสี่ยง ทั้งที่ผู้ใช้เขียนแค่ว่า "ดีๆ"

**นี่คือกลไกที่สำคัญที่สุดที่รอบนี้จับได้: กฎข้อ 9 (ระบุรูปร่างของผลลัพธ์) เป็นดาบสองคม**

รอบ 3 กฎข้อนี้ชนะที่ F23 เพราะมันแปลง "หา 1 คนที" เป็น `Pick exactly one person` แล้วได้คำตอบที่ตรงคำขอ
รอบ 4 กฎข้อเดียวกันแพ้ที่ F02 เพราะมันแปลง "หุ้นดีๆ" เป็น `state the criteria you used to judge it good` ซึ่ง **บังคับให้ model ผลิตเกณฑ์ที่ผู้ใช้ไม่เคยให้ขึ้นมาเอง** นั่นคือการ invent แบบเดียวกับที่กฎข้อ 2 ห้ามไว้ แต่มาทางประตูหลัง

การสั่งให้ผลลัพธ์มีรูปร่างชัด ได้ผลดีเมื่อรูปร่างนั้นอยู่ในคำพูดของผู้ใช้แล้ว และได้ผลเสียเมื่อมันไม่ได้อยู่

## สิ่งที่ v3 แก้ได้จริง ยืนยันได้ทั้ง 8 ข้อ

1. **ภาษา** D ตอบเป็นภาษาไทยทุกข้อ ปัญหา F25 ของรอบ 3 หายไปสนิท
2. **ช่วยรอบๆ ช่องว่าง** F11 เส้นทาง fragment ให้วิธีประเมินมูลค่ามา 7 แบบพร้อมบอกว่าแต่ละแบบต้องใช้ข้อมูลอะไร แล้วค่อยถาม ส่วน R04 อธิบายทั้งกรณี pull request และกรณีประชาสัมพันธ์ก่อนถาม ปัญหา R19 ของรอบ 3 หายไป
3. **เก็บตัวสะกดไทย** เห็นในผลจริง เช่น `(written "ควรเปิดprมั้ย")` และ `(the user wrote the genre as "แนวแอคชั่น")`

ทั้งสามข้อคือสิ่งที่ตั้งใจแก้ และแก้ได้ครบ **แต่แก้แล้วคะแนนยังแพ้**

## ที่ D ชนะแบบ checks มองไม่เห็น

**P07 "อยากสร้างโมเดลโรงแรมอัจฉริยะแบบ3Dมาหน่อย ว่าจะมีหน้าตาเป็นยังไง"**

D ส่ง **โมเดล 3 มิติที่ใช้งานได้จริง** กลับมา เป็นไฟล์ HTML + Three.js ครบทั้งตึก 10 ชั้น ล็อบบี้กระจก โซลาร์เซลล์บนดาดฟ้า จุดเซ็นเซอร์ IoT กะพริบ และปุ่มสลับกลางวันกลางคืน ส่วน baseline ถามกลับ 5 ข้อแล้วไม่ได้ทำอะไรเลย

ผู้ใช้เขียนว่า "อยากเห็นว่าหน้าตาเป็นยังไง" D ให้สิ่งนั้น baseline ไม่ให้

แต่ `checks` ของ P07 มีข้อเดียวคือ "output กล่าวถึงโมเดล 3D และคำว่าโรงแรมอัจฉริยะโดยตรง" ซึ่ง **ทั้งคู่ผ่าน** ได้ 1/1 เท่ากัน

นี่คือความล้มเหลวของเครื่องมือวัด ไม่ใช่ของ product ถ้ามีคนตัดสินด้วยสายตา D ชนะข้อนี้ขาด และถ้า P07 มี check ที่วัดว่า "ส่งของที่ขอมาจริงไหม" ผลรวมทั้งรอบจะพลิก

## ข้อจำกัด อ่านก่อนเชื่อตัวเลข −5.9

- **n = 8, รัน 1 ครั้ง** ข้อเดียว (F02) ตัดสินเครื่องหมายของผลทั้งรอบ ถ้า F02 ออกอีกทาง margin จะกลายเป็นบวก ผลนี้จึงควรอ่านว่า **"วัดความได้เปรียบไม่ได้"** ไม่ใช่ "แย่กว่าอย่างชัดเจน"
- **ผมให้คะแนนเอง ไม่ blind** และใช้ไม้บรรทัดเดียวกับรอบ 3 โดยตั้งใจ คือ "เสนอมากกว่าหนึ่งตัวเลือก = ตก" ซึ่งรอบ 3 ทำให้ baseline ตก รอบนี้ทำให้ D ตก ถ้าผ่อนกฎนี้ ผลทั้งสองรอบเปลี่ยนไปคนละทาง
- **`checks` วัดการยับยั้งชั่งใจได้ดี แต่วัดการส่งมอบไม่ได้** P07 คือหลักฐานชัดเจน ชุด checks นี้ให้รางวัลกับการถามกลับและการไม่เดา แต่ไม่ให้คะแนนกับการทำงานเสร็จ
- ยังเป็น input ของผู้ใช้คนเดียว และยังไม่มี arm A, B, C, F

## สรุปที่ตรงไปตรงมา

หลังแก้สามรอบ ตาม feedback ที่วัดได้ทุกครั้ง บน baseline ที่ยุติธรรมและชุดทดสอบที่สุ่มจริง **optimizer ยังทำคะแนนไม่ชนะการพิมพ์ประโยคภาษาไทยหนึ่งประโยคต่อท้าย**

สิ่งที่ยังเป็นความจริงคือ v3 เป็นเวอร์ชันที่ดีที่สุดในสามเวอร์ชัน มันแก้ข้อบกพร่องที่รอบก่อนวัดได้ครบทุกข้อ และมันชนะขาดในกรณีอย่าง P07 ที่ผู้ใช้อยากได้ของจริงออกมา

สิ่งที่เปลี่ยนไปคือ **สมมติฐานว่าคุณค่าอยู่ที่ไหน** สามรอบที่ผ่านมาวัดเรื่อง "AI เดาน้อยลงไหม" ซึ่งประโยคไทยหนึ่งประโยคทำได้พอๆ กัน แต่ P07 ชี้ว่าคุณค่าอาจอยู่ที่ "AI ลงมือทำเลยไหมแทนที่จะถามวนไปมา" ซึ่งเป็นคนละคำถาม และ `checks` ชุดปัจจุบันวัดมันไม่ได้เลย

ถ้าจะไปต่อ อย่าแก้ optimizer อีก **ให้แก้เครื่องมือวัดก่อน** เพิ่ม check ประเภท "ผู้ใช้ได้สิ่งที่ขอกลับไปในเทิร์นเดียวหรือไม่" แล้วรันชุดสุ่มใหม่ ถ้า margin ยังไม่บวกหลังจากนั้น คำตอบก็คือไม่ควรสร้าง และคราวนี้จะเป็นคำตอบที่เชื่อถือได้จริง
