# Pre-registration: Thai → AI-ready instruction

**ล็อกวันที่ 2026-09-16 ก่อนรันการทดลอง ก่อนเห็นตัวเลขใดๆ**

เอกสารนี้มีไว้กันตัวเองหลอกตัวเอง ห้ามแก้เกณฑ์หลังเห็นผล ถ้าจำเป็นต้องแก้จริง ให้ commit ใหม่พร้อมเหตุผล และถือว่าผลรอบก่อนหน้าเป็น exploratory ไม่ใช่ confirmatory

## สมมติฐานที่กำลังทดสอบ

การแปลง prompt ภาษาไทยธรรมชาติ ให้เป็น English instruction ที่มีโครงสร้างและเปิดเผย assumptions ทำให้ผลลัพธ์จาก LLM **ถูกต้องขึ้นอย่างมีนัยสำคัญ** เทียบกับการส่งภาษาไทยดิบ

สมมติฐานนี้ยังไม่มีงานวิจัยรองรับสำหรับภาษาไทย ดู `../research/research.md` §5

## Arms

| id | ชื่อ | คำอธิบาย | สร้างยังไง |
|---|---|---|---|
| `A` | thai_raw | ข้อความไทยดิบ ไม่แตะเลย | mechanical |
| `E` | thai_ask | ไทยดิบ + ต่อท้าย "ถ้ามีอะไรไม่ชัด ถามก่อนตอบ" | mechanical |
| `F` | thai_thai | ไทยดิบ + สั่งให้ตอบเป็นไทย | mechanical |
| `B` | thai_structured | ไทยที่จัดโครงสร้างแล้ว ยังเป็นไทย | LLM |
| `C` | english_literal | แปลตรงเป็นอังกฤษ คงความสุภาพและ hedging ไว้ | LLM |
| `D` | optimized | **ตัว product** ผ่าน pipeline ใน `optimizer.md` | LLM |

`E` คือคู่แข่งที่ถูกที่สุดในโลก ต้นทุนสิบคำ ไม่ต้องมี product
`F` ทดสอบว่าการแปลเป็นอังกฤษจำเป็นจริงไหม

**กติกาเหล็ก: `D` ต้องมาจาก pipeline อัตโนมัติเท่านั้น ห้ามมนุษย์แก้แม้แต่คำเดียว** ถ้าแก้ด้วยมือ ผลที่ได้คือของที่ ship ไม่ได้

## ตัวชี้วัด

### Primary: task success rate

ต่อ input หนึ่งอัน มี `checks` เป็นคำถาม **ใช่ หรือ ไม่ใช่** ที่ตรวจได้โดยไม่ต้องใช้วิจารณญาณ เขียนไว้ล่วงหน้าใน `inputs.json` ก่อนรัน

```
task_success_rate = checks ที่ผ่าน / checks ทั้งหมด
```

ให้คะแนนแบบ **blind** ผู้ให้คะแนนไม่รู้ว่ากำลังอ่าน output ของ arm ไหน

### Hard gate: invariant pass rate ของ D

ตรวจบน **prompt ที่ pipeline สร้าง** ไม่ใช่บน output สุดท้าย

| invariant | คำอธิบาย |
|---|---|
| `preserve` | ทุกข้อใน `must_preserve` ของ input นั้น ต้องปรากฏใน block `<optimized>` |
| `no_invention` | ห้ามมีข้อเท็จจริง ตัวเลข หรือเทคโนโลยี ที่ไม่ได้มาจาก input โผล่ใน `<optimized>` |
| `standalone` | `<optimized>` เมื่อ copy ออกมาเดี่ยวๆ ต้องยังครบ ไม่ต้องพึ่ง assumptions |

### Secondary (รายงาน แต่ไม่ใช้ตัดสิน)

- input tokens ต่อ arm วัดด้วย `messages.count_tokens` ของ model ที่ทดสอบจริง ไม่ใช้ tiktoken เป็น proxy
- จำนวนครั้งที่ model ถามกลับ แทนที่จะเดา
- ต้นทุนจริงของ pipeline (token ที่ optimizer เผา) เทียบกับที่ประหยัดได้ปลายทาง

## เกณฑ์ตัดสิน ล็อกแล้ว

อ่านตามลำดับ หยุดที่ข้อแรกที่เข้าเงื่อนไข

### 0. Gate ก่อนดูอะไรทั้งสิ้น

ถ้า **invariant pass rate ของ D น้อยกว่า 95%** → **ไม่สร้าง** ไม่ว่า task success จะดีแค่ไหน

เครื่องมือที่ทำ requirement ของผู้ใช้หาย คือเครื่องมือที่พัง การที่มันได้คะแนนสูงขึ้นแปลว่ามันเดาเก่ง ไม่ใช่ว่ามันซื่อสัตย์ และนั่นอันตรายกว่าไม่มีเครื่องมือ

### 1. เกณฑ์หลัก

เทียบ `D` กับ `E` (ไม่ใช่กับ `A`) เพราะ `E` คือสิ่งที่ผู้ใช้ทำได้ฟรีวันนี้

| ผลต่าง task success (D − E) | การตัดสินใจ |
|---|---|
| ≥ +15 pp | **สร้างต่อ** |
| +5 ถึง +15 pp | **ยังไม่สร้าง** เก็บ input เพิ่มเป็น 40 อัน แล้ววัดใหม่หนึ่งรอบ ถ้ายังอยู่ในช่วงนี้ ให้ถือว่าไม่ผ่าน |
| < +5 pp | **ไม่สร้าง** product ไม่มีคุณค่าเหนือประโยคเดียว |

### 2. คำถามรอง ที่ต้องรายงานไม่ว่าผลจะออกทางไหน

- `D` เทียบ `F`: ถ้าต่างกันน้อยกว่า 5 pp แปลว่า**การแปลเป็นอังกฤษไม่จำเป็น** ต้องเปลี่ยน positioning เป็นเครื่องมือจัดโครงสร้างภาษาไทย
- `D` เทียบ `C`: แยกผลของ "การจัดโครงสร้าง" ออกจากผลของ "การแปล"
- `B` เทียบ `D`: ถ้า `B` (ไทยมีโครงสร้าง) เท่ากับ `D` คำตอบเดียวกับข้อแรก

## ขนาดตัวอย่าง

- inputs: อย่างน้อย **20 อัน** ในจำนวนนี้ต้องมี **input สั้นกว่า 15 คำ อย่างน้อย 5 อัน**
- runs ต่อ arm ต่อ input: **3**
- ที่มาของ input: **ต้องมาจากคนจริง** ดู `inputs.json` field `provenance`

input ที่ AI สร้าง หรือที่คนทำ product เขียนเอง **ห้ามนับ** เพราะจะเอนเข้าหาสิ่งที่ pipeline ทำได้ดี

## สิ่งที่การทดลองนี้ไม่ได้ตอบ

- ผู้ใช้จะยอมจ่ายเงินไหม
- friction ของการ copy ออกไปเว็บอื่นแล้ว copy กลับ
- คุณภาพเมื่อเจอ domain ที่ pipeline ไม่เคยเห็น
- ผลกับ model อื่นนอกจากตัวที่ทดสอบ

อย่าอ้างผลการทดลองนี้เกินขอบเขตข้างบน
