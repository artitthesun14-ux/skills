# Validation experiment

ทดสอบว่าการแปลง prompt ไทย → English instruction ทำให้ผลลัพธ์ดีขึ้นจริงไหม **ก่อน** ลงมือสร้าง product

เกณฑ์ตัดสินล็อกไว้แล้วใน `PREREGISTRATION.md` อ่านก่อนรัน และอย่าแก้หลังเห็นผล

## ก่อนรัน

```bash
npm install
export ANTHROPIC_API_KEY=...   # หรือ ant auth login
```

เติม `inputs.json` ให้ครบ **20 อันที่เป็นของจริง** ตอนนี้มีแค่ 2 อันที่ติดป้าย `seed` ซึ่งใช้ debug ได้แต่ห้ามนับผล `tally` จะเตือนถ้ายังไม่มี input ที่ `provenance: "real"`

## ลำดับการรัน

```bash
node run.mjs generate          # สร้าง prompt ทั้ง 6 arm (ใช้ LLM สำหรับ B, C, D)
node run.mjs execute --yes     # รัน prompt จริง 6 arm x 3 runs
node run.mjs judge --yes       # ให้คะแนน binary แบบ blind + ตรวจ invariant ของ D
node run.mjs tally             # อ่านผลตามเกณฑ์ที่ล็อกไว้
```

อยากให้มนุษย์ให้คะแนนเองแบบไม่รู้ว่าอ่าน arm ไหน

```bash
node run.mjs sheet             # สร้าง out/sheet.md แบบสลับลำดับและไม่มี label
```

`out/answer-key.json` คือกุญแจถอดรหัส **อย่าเปิดจนกว่าจะให้คะแนนเสร็จ**

## ตัวแปรที่ปรับได้

| env | ค่าตั้งต้น | ความหมาย |
|---|---|---|
| `TASK_MODEL` | `claude-opus-5` | model ที่รับ prompt จริง |
| `JUDGE_MODEL` | `claude-opus-5` | model ที่ให้คะแนน binary |
| `RUNS` | `3` | จำนวนครั้งต่อ arm ต่อ input |
| `CONCURRENCY` | `4` | คำขอพร้อมกัน |

## ทำไมถึงออกแบบแบบนี้

การทดลองที่ออกแบบหละหลวมจะบอกว่า product ดีเสมอ ทุกอย่างข้างล่างมีไว้กันไม่ให้เป็นแบบนั้น

**arm `E` คือคู่แข่งตัวจริง** ไม่ใช่ `A` ผู้ใช้วันนี้พิมพ์ไทยแล้วต่อท้ายว่า "ถ้ามีอะไรไม่ชัด ถามก่อนตอบ" ได้ฟรี ถ้า product ชนะแค่ภาษาไทยดิบแต่ไม่ชนะประโยคเดียวนี้ แปลว่าไม่มีคุณค่า เกณฑ์หลักจึงวัด `D − E`

**arm `F` ทดสอบ premise** research หาไม่พบงานวิจัยที่วัดไทย vs อังกฤษเลย ถ้า `F` เท่ากับ `D` แปลว่าการแปลเป็นอังกฤษไม่ได้ช่วยอะไร และ product ควรเป็นเครื่องจัดโครงสร้างภาษาไทยแทน

**`D` ต้องมาจาก pipeline เท่านั้น** ห้ามแก้ด้วยมือ prompt ที่มนุษย์ขัดเกลาคือของที่ ship ไม่ได้ ถ้าผลไม่ดี ให้แก้ `optimizer.md` แล้วรันใหม่ทั้งชุด

**คะแนนเป็น binary ไม่ใช่ 1 ถึง 10** LLM judge เอนเข้าหาคำตอบที่ยาวและมีโครงสร้าง ซึ่ง `D` เป็นแบบนั้นพอดี คำถามใช่ไม่ใช่ที่เจาะจง เช่น "output มี constraint กันจองซ้อนไหม" ต้านอคตินี้ได้ดีกว่ามาก และ `checks` ต้องเขียนไว้ใน `inputs.json` ก่อนรัน

**ตัดเกณฑ์ที่วัดตัวเองออก** ไม่มี "format compliance" ในการให้คะแนน เพราะนั่นคือสิ่งที่เราสั่ง `D` ให้ทำ การที่มันทำได้ไม่ใช่ผลการทดลอง

**invariant เป็น gate ไม่ใช่คะแนน** ถ้า pipeline ทำ requirement ที่ผู้ใช้พูดแล้วหาย หรือแต่งข้อมูลเพิ่ม ผลลัพธ์ที่คะแนนสูงยิ่งอันตราย เพราะแปลว่ามันเดาเก่ง ไม่ใช่ซื่อสัตย์ `tally` จะสั่งไม่ให้สร้าง ต่อให้ `D` ชนะขาด

**นับ token ด้วย `count_tokens` ของ model จริง** ไม่ใช้ tiktoken เป็น proxy เพราะ Anthropic ไม่เปิด public tokenizer และ tokenizer ตั้งแต่ Opus 4.7 นับต่างจากรุ่นก่อนมาก ตัวเลขจาก tiktoken จะผิด

**รายงานต้นทุนของ optimizer เอง** `tally` แสดงว่า optimizer เผา token ไปเท่าไรเพื่อสร้าง `D` ตัวเลขนี้มักมากกว่าที่ประหยัดปลายทางหลายเท่า ซึ่งเป็นเหตุผลว่าทำไม token saving ถึงไม่ใช่ value proposition
