# Pilot ฟรี ไม่ใช้ API key

วันที่: 2026-09-16
วิธี: ใช้ subagent ของ Claude Code แทนการเรียก Messages API ตรง จึงไม่ต้องมี `ANTHROPIC_API_KEY` และไม่มีค่าใช้จ่ายแยก

**นี่ไม่ใช่การทดลองตาม `PREREGISTRATION.md`** อ่านหัวข้อ "ข้อจำกัด" ก่อนเชื่อตัวเลขใดๆ ในนี้

## สิ่งที่ทำ

- 5 inputs จาก 40 อัน: R02, R18, P04, F05, F16
- 2 arms: `E` (ไทยดิบ + "ถ้ามีอะไรไม่ชัด ถามก่อนตอบ") กับ `D` (optimized English)
- แต่ละ arm ส่งให้ subagent ที่**ไม่รู้ว่ากำลังถูกทดลอง** เห็นแค่ข้อความเดียวเหมือนแชทใหม่
- ให้คะแนนตาม `checks` ที่เขียนไว้ล่วงหน้าใน `inputs.json`

## ผลดิบ

| input | E | D |
|---|---|---|
| R02 เริ่ม setup ยังไงดี | 2/2 | 2/2 |
| R18 /clear แล้ว context กลับมา | 1/2 | 2/2 |
| P04 flow เลือกรองเท้า | 2/2 | 2/2 |
| F05 วิเคราะห์ PWR | 2/2 | 2/2 |
| F16 "Pwr ล่ะ" | 2/2 | 2/2 |
| **รวม** | **9/10 (90%)** | **10/10 (100%)** |

margin = **+10pp** ซึ่งตกในช่วง **INCONCLUSIVE** (+5 ถึง +15pp) ของ pre-registration แปลว่า **ยังไม่สร้าง**

หมายเหตุการให้คะแนน F05: ตอนแรก arm E ตอบด้วยการถามกลับอย่างเดียว (0/2) แต่ subagent ทำงานต่อเองแล้วไปค้นข้อมูลจริง สุดท้ายส่งคำตอบที่ครบทั้ง 4 หัวข้อ จึงได้ 2/2 ดูหัวข้อ "confound ที่เจอ" ข้างล่าง

## สิ่งที่ pilot นี้จับได้ และสำคัญกว่าตัวเลข

### 1. ผมละเมิดกฎข้อ 2 ของ optimizer เอง

F05 ต้นฉบับไทยเขียนแค่ `PWR` เฉยๆ ตอนผมเขียน optimized prompt ด้วยมือ ผมใส่เป็น `PWR (Quanta Services)` ซึ่ง **ผู้ใช้ไม่เคยพูด** นี่คือ invention ตรงตามนิยามในกฎข้อ 2 ของ `optimizer.md` เอง

บังเอิญว่าการเติมนั้น**ถูก** (ไม่มี ticker ชื่อ PWR ใน SET จริง ตัวที่ใกล้เคียงคือ PLE ของพาวเวอร์ไลน์ เอ็นจิเนียริ่ง ซึ่งเป็นคนละบริษัท) แต่การที่เดาถูกไม่ได้ทำให้มันเลิกเป็น invention pipeline ไม่มีทางรู้ล่วงหน้าว่าการเติมข้อมูลครั้งไหนจะถูก ถ้าผู้ใช้หมายถึงหุ้นตัวอื่นจริง D จะตอบผิดสนิทโดยไม่มีสัญญาณเตือนเลย ส่วน E ที่ถามกลับก่อนจะไม่พลาดแบบนั้น

### 2. Invariant gate จะไม่ผ่าน

ตรวจ optimized prompt ทั้ง 5 อันตามเกณฑ์ใน `PREREGISTRATION.md`:

| input | preserve | no_invention | standalone |
|---|---|---|---|
| R02 | ✓ | ✓ | ✓ |
| R18 | ✓ | ✓ | ✓ |
| P04 | ✓ | ✓ | ✓ |
| F05 | ✓ | **✗** | ✓ |
| F16 | ✓ | ✓ | ✓ |

14/15 = **93.3%** ต่ำกว่าเกณฑ์ 95%

ตาม pre-registration ข้อ 0: **invariant ไม่ผ่าน = ไม่สร้าง ไม่ว่าคะแนนจะดีแค่ไหน** กติกานี้ทำงานตามที่ออกแบบไว้พอดี มันจับความผิดพลาดได้ ทั้งที่คนทำผิดคือคนเขียนกฎเอง

### 3. หลักฐานตรงว่าทำไม D ต้องมาจาก pipeline เท่านั้น

`PREREGISTRATION.md` เขียนไว้ว่า "D ต้องมาจาก pipeline อัตโนมัติเท่านั้น ห้ามมนุษย์แก้แม้แต่คำเดียว" ตอนเขียนกฎนั้นเป็นเหตุผลเชิงทฤษฎี ตอนนี้มีหลักฐานจริงแล้ว: พอมนุษย์เขียน D เอง มันเผลอใส่ข้อมูลที่ช่วยตัวเองภายในการทดลองครั้งแรกเลย

### 4. ความเสี่ยงที่ยืนยันได้ การแปลเป็นอังกฤษทำให้บริบท "ผู้ถามเป็นคนไทย" หายไป

arm E ซึ่งเห็นข้อความไทย ตั้งสมมติฐานแรกว่า `PWR` อาจเป็นหุ้นไทย แล้วถามกลับก่อน ส่วน arm D ซึ่งเห็นแต่อังกฤษ ไม่มีสัญญาณนั้นเหลืออยู่เลย

ในเคสนี้คำตอบที่ถูกคือหุ้นอเมริกัน E จึงเสียเวลาไปหนึ่งรอบ แต่กลไกที่ทำให้ E ระวังคือสิ่งที่ D ไม่มี และในเคสที่ผู้ใช้หมายถึงของไทยจริง (ชื่อย่อบริษัท ชื่อหน่วยงาน ชื่อกฎหมาย มาตรฐานบัญชี ภาษี) การทิ้งบริบทภาษาจะทำให้ตอบผิดเงียบๆ

ตรงกับข้อสังเกตใน `../research/research.md` §4 ข้อ 4 ว่าการ compress คือการตัดสินใจแทนผู้ใช้ **ข้อเสนอ: เพิ่มกฎใน optimizer** ว่าสัญชาติ ตลาด ภูมิภาค หรือเขตอำนาจกฎหมาย ที่ผู้ใช้ไม่ได้ระบุ ห้ามเดา ต้องขึ้นเป็น open question เสมอ

## confound ที่เจอ ระดับความพยายามของสอง arm ไม่เท่ากัน

arm E ของ F05 ใช้ tool 15 ครั้ง ค้นเว็บ อ่าน 10-K แล้วตอบพร้อมตัวเลขจริงและแหล่งอ้างอิง ส่วน arm D ใช้ tool 1 ครั้ง ตอบจากความรู้ในตัว model พร้อมออกตัวว่าไม่มีข้อมูลราคาสด

ความต่างนี้**ไม่ได้มาจากคุณภาพของ prompt** แต่มาจากการที่ subagent ตัวหนึ่งบังเอิญทำงานต่อในโหมดที่ค้นข้อมูลได้ นี่คือตัวแปรแทรกที่ harness ตัวจริง (`run.mjs`) ไม่มี เพราะมันเรียก Messages API ตรงๆ ไม่มี tool ให้ใช้ ทั้งสอง arm จึงอยู่บนเงื่อนไขเดียวกัน

ถ้าจะรันรอบต่อไปด้วย subagent ต้อง**ปิด tool ของ subagent ทุกตัว** ไม่งั้นผลจะวัดความขยันของ agent แทนที่จะวัด prompt

## ข้อจำกัดของ pilot นี้

- n = 5 จาก 40 ไม่มีนัยสำคัญทางสถิติ
- รัน 1 ครั้งต่อ arm ไม่ใช่ 3
- **ผมเขียน arm D ด้วยมือ** ซึ่งละเมิดกติกาหลักของ pre-registration
- **ผมให้คะแนนเอง โดยรู้ว่าอันไหนเป็น arm ไหน** ไม่ใช่ blind
- ไม่มี arm A, B, C, F จึงไม่รู้ว่าการแปลเป็นอังกฤษจำเป็นจริงไหม
- subagent ที่ใช้เป็น model ของ session นี้ ไม่ใช่ `claude-opus-5` ตามที่ harness ตั้งไว้
- subagent มี tool ใช้ ทำให้ระดับความพยายามไม่เท่ากันระหว่าง arm ดูหัวข้อ confound ข้างบน

## ขั้นถัดไปที่ทำได้ฟรี

ตอนนี้ `thai-prompt-optimizer` เป็น skill จริงในรีโปแล้ว จึงรันรอบต่อไปได้โดย**ให้ skill เป็นคนสร้าง arm D เอง** ผ่าน subagent ที่เห็นแค่กฎของ skill กับข้อความไทย ไม่รู้เรื่องการทดลอง ซึ่งแก้ปัญหาข้อ 1 และ 3 ข้างบนได้ทั้งหมด และยังไม่ต้องใช้ API key

ถ้าทำแบบนั้นครบ 40 inputs × 6 arms ก็จะเป็นการทดลองตาม pre-registration จริง โดยไม่เสียเงินเพิ่ม แลกกับเวลาและ usage ของ session
